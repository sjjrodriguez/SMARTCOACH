# SmartCoach Cycling — Methodology and Architecture

Project phases document: (1) the **CRISP-DM / CRISP-ML(Q)** methodology applied to the ML models and
(2) the **4-layer software architecture** of the web application. Everything described as "exists" was checked
against the code on this branch; anything that does not exist yet is marked **Pending / proposal**.

---

## 1. Methodology: CRISP-DM / CRISP-ML(Q)

CRISP-DM defines 6 phases. CRISP-ML(Q) keeps those phases and adds **quality assurance (Q)** to each one,
plus a final **monitoring and maintenance** phase (models degrade over time).

The project has **three models**, all in `ml_engine/`:

| # | Model | Purpose | Data | Training script | Artifact |
|---|-------|---------|------|-----------------|----------|
| A | Plan classifier (Beginner / Moderate / Advanced) | Assigns the training plan level | `ciclistas_planes.csv` (1,000 **synthetic** records generated by `train_model.py`) | `train_model.py` | `model_artifacts/model.joblib` + `scaler.joblib` |
| B | Injury risk (Low / Medium / High) | Calculated when a workout is logged | `sports_injury_data.csv` (Kaggle, 15,420 rows) | `train_injury_model.py` | `model_artifacts/injury_model.joblib` |
| C | Cyclist profile (previous injury) | *Cyclist profile* screen | `DATA.xlsx` (cyclist questionnaire, 42 columns) | `train_cyclist_injury_model.py` | `models/injury_model_cyclist.joblib` |

### Phase 1 — Business understanding
- **Goal:** help a cyclist train with a plan that fits their level and **prevent injuries** by logging load and recovery.
- **Success criteria:** the cyclist gets a plan, logs workouts and receives an understandable injury risk (traffic light + probabilities + recommendations).
- **CRISP-ML(Q) — requirements and risks:** the output is **guidance, not a medical diagnosis** (this wording already appears on the dashboard). A false "low risk" is the costliest error, which is why probabilities are shown and not only the label.

### Phase 2 — Data understanding
- Source A: datos.gov.co *Supported athletes and para-athletes* (`datos_gov_ciclismo_raw.csv`, 60,000 rows; filtered to cycling → `datos_gov_ciclismo.csv`, 2,150 rows). It only has demographic variables, no load or fatigue.
- Source B: Kaggle *Multimodal Sports Injury Dataset* (15,420 rows, 29 columns). Target class distribution: 9,868 / 3,238 / 2,314 (imbalanced).
- Source C: questionnaire `DATA.xlsx`.
- The exploratory analysis is in `ml_engine/notebooks/exploratory_data.ipynb` (data quality problems found: `ID` and `Año` stored as text with a thousands separator, age ranges, etc.).
- **CRISP-ML(Q):** the notebook includes a documentation sheet for each source (the download date must be filled in before submitting).

### Phase 3 — Data preparation
- Cleaning and filtering of source A (notebook, section 3).
- Model B: only variables the cyclist can report are used: `training_intensity` (RPE), `training_duration`, `training_load` (RPE × min, calculated), `heart_rate`, `sleep_quality`, `recovery_score`, `fatigue_index`. Missing values are imputed inside the `Pipeline`.
- Model C: the form only asks the most useful questions; the remaining columns are sent empty and the `Pipeline` imputer fills them in.
- Model A: `StandardScaler` over 5 variables (`age`, `weight_kg`, `weekly_hours`, `resting_heart_rate`, `tss_acumulado`).
- **CRISP-ML(Q):** the notebook includes a **data leakage check** (splitting or not splitting by athlete), and the column order is saved in `injury_features.json` so the service builds exactly the same vector used in training.

### Phase 4 — Modeling
- Model A: Random Forest (100 trees, max depth 10) with a stratified 80/20 split.
- Model B: balanced Random Forest inside a `Pipeline` (imputer + classifier), stratified 5-fold cross-validation.
- Model C: Random Forest with `ColumnTransformer` (imputation + One-Hot).
- Algorithm comparison (Random Forest vs XGBoost) is documented in the notebook, section 4. The files `model_artifacts/metrics.json` and `features.json` (which include `age` and `bmi`) belong to an earlier version of the injury model and are kept as history.

### Phase 5 — Evaluation
| Model | Main metric | Result |
|-------|-------------|--------|
| B (injury risk) | test macro-F1 | **0.445** (cross-validation 0.442) |
| B | test accuracy | 0.474 |
| B | majority-class baseline | 0.640 |
| C (profile) | accuracy / F1 | 0.554 / 0.34 |
| A (plan) | — | **No metrics saved in the repository** (`train_model.py` only prints them). Pending: save them in `metrics/` |

**Honest reading of the results (important for the report):**
- For model B, **accuracy (0.474) is lower than the majority-class baseline (0.640)**. That is why macro-F1 is the appropriate metric and the model must be presented as **guidance only**. Where it does help: it detects the *High* class well (404 of 463 cases in the confusion matrix).
- The most important variable is `recovery_score` (importance ≈ 0.44), followed by `sleep_quality` and `fatigue_index`. This is why the workout form asks for **recovery and sleep** in the *Injury check* tab.
- Model A was trained on **synthetic** data built from rules per level; its good results reflect those rules, not real cyclists. This must be stated as a limitation.
- **Business criterion:** besides the model, the app uses explainable rules (`progress_service.py` for plan changes and `dashboard_service.py` for the weekly load traffic light) that do not depend on the model metrics.

### Phase 6 — Deployment
- Models are exported with `joblib` and the Flask app loads them lazily (`ml_service.py`, `injury_service.py`, `injury_cyclist_service.py`): if the artifacts are missing, the app still starts and the error only appears when they are used.
- PostgreSQL database (Supabase); tables are created at startup with `db.create_all()` and `schema_service.ensure_columns` adds new columns without deleting data.
- **CRISP-ML(Q) — deployment QA:** strict input validation (ranges in `injury_service.LIMITS`) and error handling that never loses a workout (if the model fails, the workout is still saved and the user is notified).

### Phase 7 (CRISP-ML(Q) only) — Monitoring and maintenance
**Pending / proposal** (not yet in the code):
- Store every prediction (already done in `injury_checkins`: level and probabilities) and compare it with injuries actually reported to measure real-world performance.
- Retrain once there are enough real records and version the artifacts (`injury_model_v2.joblib`).
- Watch for data drift (for example, the users' average `recovery_score` versus the training dataset).

## 2. Software architecture: 4 layers

Rule: each layer only uses the layer below it. Templates never talk to the database.

```
┌───────────────────────────────────────────────────────────────┐
│ 1. PRESENTATION         app/templates/ + app/static/          │
│    Jinja2, Bootstrap 5, Chart.js, workout_form.js             │
├───────────────────────────────────────────────────────────────┤
│ 2. APPLICATION / CONTROL   app/controllers/                   │
│    Flask blueprints: auth, main, workouts, plans, injury      │
├───────────────────────────────────────────────────────────────┤
│ 3. BUSINESS LOGIC          app/services/ + ml_engine/         │
│    rules, traffic light, routines, validation, ML models      │
├───────────────────────────────────────────────────────────────┤
│ 4. DATA                    app/models/ + database             │
│    SQLAlchemy (User, Workout, TrainingPlan, InjuryCheckin)    │
│    PostgreSQL (Supabase), .joblib artifacts, CSV/XLSX         │
└───────────────────────────────────────────────────────────────┘
```

| Layer | Folder / files | Responsibility | Example in the project |
|-------|----------------|----------------|------------------------|
| 1. Presentation | `templates/` (`base.html`, `workouts/_form.html`, `dashboard/index.html`…), `static/css`, `static/js` | Show data and collect forms | The workout form has 2 tabs: *Workout* and *Injury check* |
| 2. Application / Control | `controllers/auth.py`, `main.py`, `workouts.py`, `plans.py`, `injury.py` | HTTP routes, user session, orchestrate use cases, redirects | `workouts.create_workout` saves the workout and triggers the injury check |
| 3. Business logic | `services/injury_service.py` (validation + model B), `ml_service.py` (model A), `injury_cyclist_service.py` (model C), `dashboard_service.py` (load traffic light), `routine_service.py`, `progress_service.py`; training code in `ml_engine/` | Rules and predictions, independent of Flask | `risk_from_workload()`, `InjuryService.predict()` |
| 4. Data | `models/*.py`, `config.py`, `ml_engine/data`, `model_artifacts/`, `schema_service.py`, `seed_service.py` | Persistence and data access | Tables `injury_checkins`, `workouts`, `training_plans`, `users` |

### Example flow: logging a workout
1. **Presentation:** the cyclist fills in the *Workout* tab and the *Injury check* tab (recovery, sleep, optional heart rate).
2. **Control:** `workouts.create_workout` validates the form.
3. **Business logic:** `injury_service` builds the feature vector (RPE, duration and fatigue come from the workout) and model B predicts the risk.
4. **Data:** `Workout` and `InjuryCheckin` are saved; the controller redirects to the result.

### Architecture notes (honest)
- The layers are well separated overall: `dashboard_service`, `routine_service` and `progress_service` are pure functions with no Flask or database dependency, which makes them easy to test.
- There is a small logic leak in the controller: `workouts._check_data` and `_run_daily_check` build the injury check inside `controllers/workouts.py`. **Proposal:** move them to `services/injury_service.py` in a future iteration.
- Controllers query the SQLAlchemy models directly (there is no repository layer). For a project of this size that is acceptable.

## 3. Changes in this iteration (traceability)

| Requirement | What was done |
|-------------|---------------|
| Remove the separate *Daily injury check-in* page | Removed the `/injury/checkin` route, the `injury/checkin.html` template and every button/link that led to it (dashboard, history, result, plan). |
| Remove the estimated TSS | Removed from the form, the summary, the workout list, the server calculation and the dashboard text. Load is now always **RPE × minutes**. | Injury check filled in from the workout | RPE, duration and fatigue are taken automatically from the workout (shown in tab 2); the check is created and saved automatically when the workout is saved. |
| Show the phases inside the application | Three public pages in the top navigation bar: **Phases** (`/phases`), **Architecture** (`/architecture`) and **Project document** (`/project-document`), each with Next / Back buttons. Metrics are read from the model JSON files, so they never go out of date. |
